# Contributing to Klask

Thanks for your interest in Klask. Bug reports, documentation fixes, ideas and
code are all welcome. By taking part you agree to follow the
[code of conduct](CODE_OF_CONDUCT.md).

Found a security problem? Do not open a public issue: follow
[SECURITY.md](SECURITY.md).

## Reporting a bug or asking for a feature

Search the [existing issues](https://github.com/klask-dev/klask-dev/issues)
first, then open a new one with the matching template. For a bug, include the
Klask version (shown in the interface and at `/version` on the backend), how you
deploy it (Docker Compose, Helm, from source), what you did, what you expected
and what happened, plus relevant backend logs. For a larger change, open an issue
to discuss the idea before writing code.

## Setting up

The full steps are in [docs/dev/development.md](docs/dev/development.md). In short:

```bash
# database
docker compose -f docker-compose.dev.yml up -d postgres

# backend (http://localhost:3000)
cd klask-rs && cp .env.example .env && cargo run --bin klask-rs

# frontend (http://localhost:5173), in another terminal
cd klask-react && npm install && npm run dev
```

You need a recent stable Rust toolchain (1.88 or newer), Node.js 22 and Docker.
The first account created through the web interface is the administrator.

## Before you open a pull request

Run the checks the CI runs (details in [docs/dev/testing.md](docs/dev/testing.md)):

```bash
# backend
cd klask-rs
cargo fmt -- --check
cargo clippy -- -D warnings
cargo test

# frontend
cd klask-react
npm run lint
npm run typecheck
npm run test:ci
```

`make install-hooks` installs git hooks that run the quick checks on commit and
the heavier ones on push.

Please also:

- add or update tests for the behaviour you change;
- update the documentation in `docs/` or the README when behaviour,
  configuration or commands change;
- keep the pull request focused on one subject, and describe what changed and
  why. Link the issue it closes (`Closes #123`).

Do not edit `CHANGELOG.md` and do not bump versions: both are generated by the
release process.

## Commit messages

Releases are automated by semantic-release, which reads commit messages that
follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<optional scope>): <short summary>
```

| Type | Use for | Effect on the version |
|---|---|---|
| `feat` | a new feature | minor |
| `fix` | a bug fix | patch |
| `perf` | a performance improvement | patch |
| `docs` | documentation only | none |
| `refactor` | a change that neither fixes a bug nor adds a feature | none |
| `test`, `chore`, `ci`, `build` | tests, maintenance, pipelines | none |

A breaking change is marked with `!` after the type (`feat!: ...`) or a
`BREAKING CHANGE:` footer, and triggers a major version. Examples:

```
feat(search): add a language filter
fix(crawler): skip files larger than the configured limit
docs: describe the MCP endpoint
```

If your pull request is squash-merged, its title is what counts: write it in this
format too.
